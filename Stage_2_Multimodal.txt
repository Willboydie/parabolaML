MULTIMODAL BALL CATCHING - STAGE 2 PLAN
Two balls: MSE BC vs oracle vs MDN
Written 2026-11-05
 
======================================================================
FIXED DECISIONS
======================================================================
 
- The random-choice expert is already implemented. It gets verified
  in step 2, not rebuilt.
- Balls are encoded with DeepSets (details in step 0).
- 2,000 two-ball training episodes.
- Two-ball models are trained on two-ball data only. No one-ball data
  is mixed in.
- Backbone rule: every compared model (one-ball ceiling, two-ball MSE,
  oracle, MDN) uses the same encoder, trunk, chunking, rate, data
  recipe and catch radius. Only the head or the oracle flag differs.
  If the backbone changes later, re-measure all of them.
 
======================================================================
STEPS
======================================================================
 
0. FREEZE THE BACKBONE AND BUILD THE DEEPSETS ENCODER
   a. Decide whether to run the along-track offset round (along-track
      sigma ~55 mm) first. Run it or skip it, but decide now.
   b. DeepSets ball encoder.
      Plain version: one small network looks at each ball on its own,
      then the results are added together. Ball order can't matter,
      and the same code handles one ball or two.
      - Per-ball input, for each frame of the 0.5 s stack (13 frames):
          world-frame position, velocity, acceleration          (9)
          base-frame position, velocity, acceleration           (9)
          ball minus end effector, base frame                   (3)
          oracle flag (0/1; constant 0 for non-oracle models)   (1)
        That is 22 numbers per frame, or 286 per ball for the full
        stack.
      - phi: a shared MLP applied to each ball's stacked features.
        Default 2 x 256 ReLU, giving a 128-D embedding.
      - Pool by summing the ball embeddings. Record the pooling
        choice in the config.
      - Robot state (time, base pose and velocity, arm joints, wheels,
        end effector), stacked as now, is concatenated with the pooled
        ball embedding and fed to the existing 3 x 512 trunk.
      - Normalise per-ball inputs with statistics pooled over all
        balls, not per slot.
   c. Unit test: swap the two balls' order and check that the output
      is unchanged up to float rounding. Log the largest difference.
   d. This is a backbone change, so retrain the one-ball model with
      the DeepSets encoder (a set of one ball) on the current one-ball
      data. Use 3 seeds and the same 200 test seeds. Compare it with
      the current best (38.2 mm mean miss). If it is clearly worse,
      fix the encoder before going on.
   e. Check the one-ball models' three checkpoints are distinct
      (weight hashes differ). This is the old loose end.
 
1. SET THE CATCH RADIUS
   a. From the step-0d model's test rollouts, compute catch rate
      against radius (for example 10 to 200 mm in 5 mm steps).
   b. Pick the smallest radius with over 80% catch.
   c. Re-score that model at this radius. This is the ceiling.
   d. Required ball separation: the two intercept points must be at
      least ~4x the radius apart. Plain version: if the balls land
      close together, aiming at the midpoint still catches one, and
      the averaging failure can't show up.
 
2. VERIFY THE EXPERT, THEN GENERATE 2,000 TWO-BALL EPISODES
   a. Verify the existing random-choice expert, on about 100 seeds:
      - It picks uniformly among reachable balls (about 50/50).
      - The choice is independent of slot order and of ball features.
      - It commits: chosen_ball never changes during an episode.
      - chosen_ball is logged.
      - Unreachable balls are excluded or resampled, and both the rule
        and the resample counts are logged.
      - Catch rate is about 100% at the chosen radius and at 10 mm,
        and the miss is close to the one-ball expert's.
   b. Scene generation:
      - Both balls launch within a short window.
      - The intercept separation is at least ~4x the radius. Check this
        on the generated data before training.
   c. Same structure as the latest one-ball set:
      - half the episodes with DART noise and clean labels;
      - offset-parking goal shifts (sideways sigma 48 mm, along-track
        sigma 19 mm or ~55 mm per step 0a, cap 150 mm, no yaw);
      - labels are the executed commands;
      - 1 kHz logs, then build_dataset to the 50 Hz grid.
   d. 200 two-ball test seeds from a new, separate seed stream.
   e. Success means catching either ball.
 
3. TRAIN TWO-BALL MSE AND THE ORACLE (two-ball data only)
   a. Two-ball MSE: same backbone and head as the ceiling.
   b. Oracle: identical, but the chosen ball's flag is set to 1 during
      training. At test time, set the flag on one reachable ball
      picked at random.
      Plain version: the oracle is told which ball to catch, so it
      separates "can't choose a ball" from "can't intercept".
   c. 3 seeds each, the same 200 two-ball test seeds, the chosen
      radius.
   d. Metrics:
      - catch rate
      - miss distance
      - between-miss rate (the share of misses where the hand ends
        nearer the midpoint than either ball)
      - target switches per episode
      - commitment time
      - catch rate against radius
      - catch rate split by caught ball and by slot
 
4. READ THE RESULT, THEN BUILD THE MDN
   a. Decision table:
      - Oracle near the ceiling, MSE well below with many
        between-misses: the averaging gap is real. Build the MDN.
      - Oracle well below the ceiling: the second ball hurts for
        another reason (inputs, separation, data, encoder). Fix this
        before judging the MDN.
      - MSE near the ceiling: rethink. The likely reason is that the
        robot's own motion reveals the choice early, so the ambiguity
        is short-lived. Check the between-miss rate and commitment
        time, and consider wider separation or later commitment
        pressure.
   b. MDN:
      - Same backbone. K = 5 Gaussian components over the full
        50 x 18 = 900-number chunk.
      - Weights pi by softmax; sigma by softplus plus a ~0.01 floor.
      - Loss: negative log-likelihood, computed with logsumexp.
   c. Run time: re-plan every 1 s and execute chunks as predicted.
      - No temporal ensembling.
      - No holding one component index per episode, because component
        labels aren't stable across predictions.
      - Compare two selection rules: highest weight, and the component
        whose chunk best continues the one being executed.
   d. Watch for collapse onto one component, for instability, and for
      switching between balls.
 
5. ITERATE THE MDN
   a. Target: match the ORACLE, which is the best achievable with two
      balls present. The one-ball ceiling is a secondary reference.
   b. If it catches but switches a lot: use the consistency rule,
      longer execution or a sticky choice.
   c. Time-box it. Fallbacks:
      - a classification head over ball or cluster with per-cluster
        regression;
      - stretch goal: a diffusion policy with an MLP denoiser
        (observation, noisy chunk, noise level) over the same chunks.
